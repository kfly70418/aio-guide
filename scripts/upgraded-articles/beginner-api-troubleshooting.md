## 开头：先停止连续重试，记录完整错误信息

连接失败时反复点击"发送"，可能触发更严格的限流，也可能让多条失败请求同时扣费。正确的做法是：立即停止重试，截图完整报错，记录发生时间、使用的客户端、模型名称，然后按本文的五层排查顺序系统化定位问题。

**核心原则**：
- ❌ 不要盲目重试（浪费钱，可能触发限流）
- ❌ 不要只说"用不了"（无法定位问题）
- ✅ 系统化排查，一次改一个变量
- ✅ 记录完整错误信息，方便联系客服

**适用人群**：
- 第一次遇到 API 错误，不知道从哪里开始查
- 看到 401、404、429 等错误代码，不知道什么意思
- 想建立系统化的故障排查能力，而不是每次都求助客服

## 准备工作

### 你需要记录的关键信息

在开始排查前，先收集以下信息（后续每一步都会用到）：

**① 完整错误信息**（截图或复制）
```
示例：
Error: 401 Unauthorized
{"error":{"message":"Incorrect API key provided","type":"invalid_request_error"}}
```

**② 发生时间**
```
示例：2026-08-14 14:30
```

**③ 使用环境**
- 客户端名称和版本（如 Chatbox 1.3.5）
- 操作系统（Windows 11 / macOS 14 / Ubuntu 22.04）
- 网络环境（家庭宽带 / 公司网络 / 移动热点）

**④ 服务商信息**
- 服务商名称（如 OpenOx、UU API）
- 使用的模型（如 gpt-4、claude-3-sonnet）
- Base URL（如 https://api.openox.tech/v1）

**⑤ 操作历史**
- 之前是否正常使用过？
- 最近是否修改过配置？
- 是否刚充值或刚创建密钥？

### 五层排查模型

本文按以下五层顺序排查（从最容易到最难）：

```
第 1 层：账户状态（余额、封禁、维护）
  ↓
第 2 层：配置正确性（密钥、地址、模型名）
  ↓
第 3 层：请求合法性（长度、格式、功能支持）
  ↓
第 4 层：网络可达性（DNS、代理、防火墙）
  ↓
第 5 层：限流和配额（频率、用量、上游限制）
```

**预计时间**：
- 简单问题（账户、配置）：5-10 分钟
- 复杂问题（网络、限流）：20-30 分钟
- 需要客服介入：1-24 小时

## 详细步骤

### 第 1 层：确认账户状态

**操作**：
登录服务商控制台，检查账户是否正常。

**填写**（账户状态检查清单）：

**① 余额检查**
```
当前余额：______ 元
最低可用余额：______ 元（通常为 0.1-1 元）
```
⚠️ 注意：
- 余额显示 ¥0.50，但最低可用余额是 ¥1
- 结果：无法发起请求，显示 402 或 429 错误

**② 账户状态**
```
[  ] 正常
[  ] 已暂停
[  ] 已封禁
[  ] 待验证
```

**③ 系统公告**
- 访问服务商首页或控制台顶部
- 查看是否有"维护公告"或"服务异常"提示

**④ 模型可用性**
- 在控制台 → 模型列表
- 确认你使用的模型（如 gpt-4）是否显示"可用"状态

**验证**：
如果以下任一项为"否"，直接跳到"解决方案"：
- ✅ 余额 > 最低可用余额
- ✅ 账户状态 = 正常
- ✅ 无维护公告
- ✅ 模型状态 = 可用

**解决方案**（如果账户异常）：

| 问题 | 解决方法 |
|------|---------|
| 余额不足 | 充值并等待 1-2 分钟生效 |
| 账户暂停 | 联系客服解除（通常因违规或欠费） |
| 系统维护 | 等待维护结束或切换备用服务商 |
| 模型下线 | 切换到其他可用模型 |

**结果**：
- ✅ 账户状态正常 → 继续第 2 层排查
- ❌ 账户异常 → 按上表解决后重试

### 第 2 层：重新核对配置

**操作**：
从控制台重新复制三项关键配置，不要凭记忆或手动输入。

**填写**（配置核对表）：

**① API Key 检查**

| 检查项 | ✅/❌ | 说明 |
|--------|------|------|
| 前后无空格 |  | 复制时不小心多选了空格 |
| 完整长度（48-51 字符） |  | 没有复制完整 |
| 以 `sk-` 开头（OpenAI 系） |  | 不同服务商前缀不同 |
| 在控制台中状态为"启用" |  | 密钥可能被禁用 |
| 未过期 |  | 部分服务商密钥有有效期 |

**验证方法**：
```bash
# 检查 API Key 长度
echo -n "你的API_KEY" | wc -c
# 应该输出 48-51

# 检查前后是否有空格
echo "你的API_KEY" | od -c
# 不应该看到开头或结尾有空格字符
```

---

**② Base URL 检查**

| 检查项 | ✅/❌ | 常见错误 |
|--------|------|---------|
| 协议头完整（https://） |  | 误写成 http:// 或缺失 |
| 包含正确路径（/v1） |  | 丢失 /v1 或误加 /v1/ |
| 没有多余路径 |  | 误加 /chat/completions |
| 与服务商文档一致 |  | 复制了错误的示例 |

**常见错误对比**：

| 错误示例 | 正确示例 | 问题 |
|---------|---------|------|
| `http://api.openox.tech/v1` | `https://api.openox.tech/v1` | 协议错误 |
| `https://api.openox.tech` | `https://api.openox.tech/v1` | 缺少路径 |
| `https://api.openox.tech/v1/` | `https://api.openox.tech/v1` | 多余斜杠 |
| `https://openox.tech/v1` | `https://api.openox.tech/v1` | 域名错误 |

**验证方法**：
```bash
# 测试 Base URL 可达性
curl -I https://api.openox.tech/v1/models

# 预期结果（成功）：
HTTP/2 401  # 没密钥，返回 401 是正常的

# 预期结果（失败）：
curl: (6) Could not resolve host  # DNS 错误
curl: (7) Failed to connect       # 网络不通
```

---

**③ Model ID 检查**

| 检查项 | ✅/❌ | 常见错误 |
|--------|------|---------|
| 拼写完全正确 |  | gpt4 → gpt-4（少连字符） |
| 大小写正确 |  | GPT-4 → gpt-4（大小写敏感） |
| 包含正确后缀 |  | claude-3 → claude-3-sonnet |
| 服务商支持该模型 |  | 用了服务商没有的模型 |

**验证方法**：
1. 到服务商控制台 → 模型列表
2. 找到你要用的模型
3. 点击"复制模型 ID"按钮（不要手打）
4. 粘贴到客户端配置中

**结果**：
- ✅ 三项配置都正确 → 继续第 3 层排查
- ❌ 发现错误 → 修正后重试，通常立即解决

### 第 3 层：用最短请求测试

**操作**：
排除复杂功能的影响，用最简单的请求测试基础连接。

**填写**（功能排查清单）：

**步骤 1：新建空白对话**
- 点击客户端的"新建对话"按钮
- 确保没有历史上下文

**步骤 2：关闭所有扩展功能**

| 功能 | 关闭 | 说明 |
|------|------|------|
| 联网搜索 | ✅ | 可能触发额外费用或权限问题 |
| 图片上传 | ✅ | Vision 功能可能不支持 |
| 文件上传 | ✅ | 可能超过长度限制 |
| 工具调用（Function Calling） | ✅ | 部分模型不支持 |
| 长上下文模式 | ✅ | 可能触发限流 |

**步骤 3：发送最短测试文本**
```
测试文本（复制使用）：
Hi

预期回复：
Hello! How can I help you today?
（或类似的简短问候）
```

**验证**：

**场景 A：短请求成功**
```
说明：基础配置正确，问题在于：
- 之前的请求太长（超过上下文限制）
- 使用了不支持的功能（如图片）
- 历史对话累积导致超长

解决方法：
1. 清理历史对话
2. 减少单次输入长度
3. 关闭不必要的功能
```

**场景 B：短请求仍然失败**
```
说明：问题在基础层（网络、限流、服务商）
继续第 4、5 层排查
```

**结果**：
记录短请求的测试结果，用于缩小问题范围。

### 第 4 层：网络可达性检查

**操作**：
确认客户端能否访问 API 服务器。

**填写**（网络检查清单）：

**① DNS 解析检查**
```bash
# Windows
nslookup api.openox.tech

# macOS / Linux
dig api.openox.tech

# 预期结果：
应该返回一个或多个 IP 地址
如果返回 "can't find" 或 "NXDOMAIN"，说明 DNS 解析失败
```

**解决方法**（DNS 失败）：
```
1. 切换 DNS 服务器（如 8.8.8.8、1.1.1.1）
2. 清空 DNS 缓存：
   Windows: ipconfig /flushdns
   macOS: sudo dscacheutil -flushcache
   Linux: sudo systemd-resolve --flush-caches
3. 等待 1-2 分钟后重试
```

---

**② 网络连通性检查**
```bash
# 测试能否访问 API 服务器
curl -I https://api.openox.tech/v1/models

# 预期结果（成功）：
HTTP/2 200 或 HTTP/2 401

# 预期结果（失败）：
curl: (7) Failed to connect
```

**解决方法**（连接失败）：
```
1. 检查防火墙设置
2. 关闭 VPN/代理后重试
3. 切换到手机热点测试
4. 联系网络管理员
```

---

**③ 代理冲突检查**

| 场景 | 问题 | 解决方法 |
|------|------|---------|
| 使用了 VPN | 可能与客户端代理冲突 | 关闭 VPN 重试 |
| 系统代理设置 | 客户端继承了错误代理 | 检查系统网络设置 |
| 客户端内置代理 | 配置错误或过期 | 检查客户端代理设置 |

**结果**：
- ✅ 网络正常 → 继续第 5 层排查
- ❌ 网络不通 → 按上述方法解决后重试

---

### 第 5 层：限流和配额检查

**操作**：
确认是否触发了请求频率限制或用量配额。

**填写**（限流检查清单）：

**① 请求频率限制**

| 错误代码 | 含义 | 常见原因 |
|---------|------|---------|
| 429 Rate Limit | 请求过快 | 短时间内发送过多请求 |
| 429 Quota Exceeded | 配额用完 | 达到每日/每月限额 |
| 429 Insufficient Quota | 余额不足 | 账户余额低于最低阈值 |

**解决方法**：

| 问题 | 解决方法 |
|------|---------|
| 短时间请求过多 | 等待 1-5 分钟后重试 |
| 达到每日限额 | 等到次日或联系客服提升 |
| 并发过高 | 减少同时打开的对话窗口 |
| 余额不足 | 充值 |

**结果**：
- ✅ 找到限流原因 → 按上述方法解决
- ❌ 仍然无法定位 → 联系客服

### 常见状态码速查

| 错误代码 | 问题层 | 快速检查 |
|---------|-------|---------|
| 401 Unauthorized | 配置 | API Key 错误或过期 |
| 403 Forbidden | 账户/网络 | 账户被封或 IP 被限 |
| 404 Not Found | 配置 | Base URL 或 Model ID 错误 |
| 429 Too Many Requests | 限流 | 请求过快或配额用完 |
| 500 Internal Server Error | 服务商 | 服务商内部错误 |
| 502 Bad Gateway | 服务商 | 上游连接失败 |
| 503 Service Unavailable | 服务商 | 服务维护中 |
| 504 Gateway Timeout | 网络/请求 | 请求太慢或网络不稳定 |
| Connection Timeout | 网络 | 无法连接到服务器 |

## 常见错误

### 错误 1：看到错误就重试

**错误做法**：
连续重试 10 次，浪费钱且触发限流。

**正确做法**：
停止 → 截图 → 按五层顺序排查 → 定位问题后再重试。

---

### 错误 2：只看错误代码，不看详细信息

**错误认识**：
"看到 401 就是密钥错误。"

**真实情况**：
401 可能有多种原因：密钥错误、过期、禁用、余额不足。

**正确做法**：
截图完整的 JSON 错误信息。

---

### 错误 3：一次改多个变量

**错误做法**：
同时换密钥、URL、模型、客户端。

**正确做法**：
保持其他不变，一次只改一个变量。
