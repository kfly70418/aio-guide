## 开头

AI API 服务质量测试的目的是：在充值前验证稳定性、对比多个平台、监控长期服务质量变化。本文给出一套可重复的评测流程：定义最低要求、准备固定测试集、分时段重复测试、记录 5 个核心指标。这套方法能将"主观印象"转化为"可对比的数据"，测试成本约 ¥5-10，耗时 1-2 小时。

## 准备工作

开始测试前，你需要：

**测试对象**：
- 2-3 个候选平台（从本站排行榜选择）
- 每个平台充值 ¥5-10（仅用于测试）
- 为每个平台创建专用测试密钥

**测试工具**：
- 客户端（如 Chatbox / Cherry Studio）或测试脚本
- Excel 或 Google Sheets（记录测试结果）
- 计时工具（手机秒表或浏览器计时）

**测试材料**：
- 准备 5 个固定测试任务（见下文）
- 准备非敏感的测试文本（不包含隐私信息）

**预计时间**：
- 单个平台测试：30-40 分钟
- 3 个平台对比：1.5-2 小时

**预计成本**：
- 单个平台：¥2-3
- 3 个平台：¥6-9

**目标**：
- 得到可对比的数据（成功率、响应时间、成本）
- 淘汰不符合最低要求的平台
- 为长期选择提供决策依据

## 详细步骤

### 第 1 步：先定义"好用"

**问题**：

不同用户对"好用"的定义不同：
- 聊天用户：最在意响应速度
- 批量程序：最在意成功率
- 长文任务：最在意内容完整性

**操作**：

在测试前写下你的最低要求。

**最低要求清单**：

| 指标 | 聊天用户 | 批量程序 | 长文任务 | 你的要求 |
|------|---------|---------|---------|---------|
| 成功率 | > 95% | > 98% | > 95% | ___ |
| 首字延迟 | < 2 秒 | < 5 秒 | < 3 秒 | ___ |
| 完整响应 | < 30 秒 | < 60 秒 | < 120 秒 | ___ |
| 格式准确性 | 不要求 | 必须 | 不要求 | ___ |
| 单次预算 | < ¥0.5 | < ¥0.2 | < ¥2 | ___ |

**示例 1：聊天用户**
```
最低要求：
- 成功率 > 95%（偶尔失败可以接受）
- 首字延迟 < 2 秒（需要流畅体验）
- 完整响应 < 30 秒（不能等太久）
- 格式准确性：不要求（可以手动调整）
- 单次预算 < ¥0.5（日常聊天成本）
```

**示例 2：批量程序**
```
最低要求：
- 成功率 > 98%（失败需要人工处理，成本高）
- 首字延迟 < 5 秒（不敏感）
- 完整响应 < 60 秒（可以等）
- 格式准确性：必须（JSON 格式错误会导致程序崩溃）
- 单次预算 < ¥0.2（需要批量处理，成本敏感）
```

**示例 3：长文任务**
```
最低要求：
- 成功率 > 95%（偶尔失败可以重试）
- 首字延迟 < 3 秒（需要确认已开始处理）
- 完整响应 < 120 秒（长文需要时间）
- 格式准确性：不要求（可以手动调整）
- 单次预算 < ¥2（长文任务价值高，对成本不太敏感）
```

**填写你的最低要求**：

```

使用场景：[描述你的主要用途]

最低要求：
- 成功率 > ____%
- 首字延迟 < ___ 秒
- 完整响应 < ___ 秒
- 格式准确性：[必须/不要求]
- 单次预算 < ¥___

优先级排序：
1. [最重要的指标]
2. [第二重要]
3. [第三重要]
```

### 第 2 步：准备固定测试集

**操作**：

准备 5 个固定测试任务，涵盖不同难度和类型。

**测试任务 1：短问答**

**目的**：测试基本功能和响应速度

**任务内容**：
```
提示词：请用一句话解释什么是 API。

预期输出：
- 长度：30-50 字
- 响应时间：< 5 秒
```

**评分标准**：
- ✅ 回答准确、简洁
- ❌ 回答过长（> 100 字）或不相关

**测试任务 2：中文长文总结**

**目的**：测试中文理解和总结能力

**任务内容**：
```
提示词：把下面文章总结为 3 点，每点 50 字以内。

[粘贴一段 500 字的中文文章]

预期输出：
- 格式：3 点列表
- 长度：150 字左右
- 响应时间：< 20 秒
```

**评分标准**：
- ✅ 准确总结为 3 点，每点简洁
- ⚠️ 总结准确但格式不符（如 5 点）
- ❌ 总结不准确或遗漏关键信息

**测试任务 3：严格格式输出（JSON）**

**目的**：测试格式控制能力

**任务内容**：
```
提示词：从下面文本中提取姓名、日期和金额，输出为 JSON 格式。

文本："张三在 2026 年 8 月 14 日支付了 150.50 元。"

预期输出：
{
  "name": "张三",
  "date": "2026-08-14",
  "amount": 150.50
}

响应时间：< 10 秒
```

**评分标准**：
- ✅ JSON 格式正确，字段完整
- ⚠️ JSON 格式正确但字段名不同
- ❌ JSON 格式错误或输出为纯文本

**测试任务 4：容易遗漏条件的任务**

**目的**：测试理解细节的能力

**任务内容**：
```
提示词：列出 10 以内的质数，要求升序排列，用逗号分隔。

预期输出：2, 3, 5, 7

响应时间：< 5 秒
```

**评分标准**：
- ✅ 输出 2, 3, 5, 7（完全正确）
- ⚠️ 输出正确但格式不符（如换行）
- ❌ 包含 1 或 9（不是质数）

**测试任务 5：你的真实工作任务**

**目的**：测试实际使用场景

**任务内容**：
```
[填写你最常用的任务]

例如：
- 代码生成：实现一个 Python 冒泡排序
- 数据提取：从销售报表中提取月度总额
- 翻译：将产品说明翻译为英文

预期输出：[描述预期结果]
响应时间：< ___ 秒
```

**评分标准**：
- ✅ [你的标准]
- ⚠️ [你的标准]
- ❌ [你的标准]

**测试集要求**：

1. **每个平台使用相同的提示词**：
   - 不要根据平台调整提示词
   - 否则无法公平对比

2. **保留原始结果**：
   - 截图或复制完整输出
   - 记录响应时间
   - 记录成功/失败状态

3. **使用相同的模型**：
   - 如果对比 Claude Opus 5，所有平台都用 Opus 5
   - 不要一个用 Opus，另一个用 Sonnet

### 第 3 步：分时段重复测试

**问题**：

单次测试无法反映稳定性，需要在不同时段重复测试。

**操作**：

在 3 个不同时段分别测试。

**时段 1：工作日白天（9:00-12:00）**

**目的**：测试正常工作时间的性能

**操作**：
1. 在工作日上午选择 1 个时间点
2. 依次执行 5 个测试任务
3. 每个任务重复 3 次
4. 记录成功率、响应时间、输出质量

**时段 2：晚间高峰（19:00-22:00）**

**目的**：测试高负载时的性能

**操作**：
1. 在工作日晚上选择 1 个时间点
2. 依次执行 5 个测试任务
3. 每个任务重复 3 次
4. 对比白天和晚间的性能差异

**时段 3：周末（周六或周日，任意时间）**

**目的**：测试周末的性能

**操作**：
1. 在周末选择 1 个时间点
2. 依次执行 5 个测试任务
3. 每个任务重复 3 次
4. 对比工作日和周末的性能差异

**重复测试的原因**：

1. **单次测试不可靠**：
   - 偶尔的快速响应不代表长期稳定
   - 偶尔的失败可能是网络抖动

2. **时段差异明显**：
   - 晚间高峰可能比白天慢 50-200%
   - 部分平台周末性能更好（商业用户减少）

3. **3 次重复足够**：
   - 更多次数成本增加
   - 3 次已能反映稳定性

**测试记录表**：

```
平台：API Xuan
模型：claude-opus-5
测试日期：2026-08-14

【任务 1：短问答】

时段 1（白天）：
- 第 1 次：成功，2.1 秒，输出质量 ✅
- 第 2 次：成功，1.8 秒，输出质量 ✅
- 第 3 次：成功，2.3 秒，输出质量 ✅
- 平均：2.1 秒，成功率 100%

时段 2（晚间）：
- 第 1 次：成功，3.5 秒，输出质量 ✅
- 第 2 次：成功，4.2 秒，输出质量 ✅
- 第 3 次：失败，超时
- 平均：3.9 秒，成功率 67% ⚠️

时段 3（周末）：
- 第 1 次：成功，2.0 秒，输出质量 ✅
- 第 2 次：成功，2.2 秒，输出质量 ✅
- 第 3 次：成功，1.9 秒，输出质量 ✅
- 平均：2.0 秒，成功率 100%

【结论】
晚间性能明显下降，成功率 67%，不符合最低要求（> 95%）⚠️
```

### 第 4 步：记录五个指标

**操作**：

对每个测试任务记录 5 个核心指标。

**指标 1：请求成功率**

**计算方法**：
```
成功率 = 成功次数 / 总次数 × 100%
```

**示例**：
```
任务 1（短问答）：
- 总次数：9 次（3 时段 × 3 次）
- 成功次数：8 次
- 成功率：88.9%
```

**评分标准**：
- ✅ > 98%：优秀
- ✅ 95-98%：良好
- ⚠️ 90-95%：一般
- ❌ < 90%：不合格

**指标 2：首字延迟**

**定义**：从发送请求到收到第一个字的时间

**测量方法**：
- 客户端：手动计时（按发送到看到首字）
- 脚本：记录 `first_token_time - request_time`

**示例**：
```
任务 1（短问答）：
- 第 1 次：2.1 秒
- 第 2 次：1.8 秒
- 第 3 次：2.3 秒
- 平均：2.1 秒
```

**评分标准**：
- ✅ < 2 秒：优秀（流畅）
- ✅ 2-5 秒：良好（可接受）
- ⚠️ 5-10 秒：一般（略慢）
- ❌ > 10 秒：不合格（明显卡顿）

**指标 3：完整响应耗时**

**定义**：从发送请求到收到完整回复的时间

**测量方法**：
- 客户端：手动计时（按发送到停止输出）
- 脚本：记录 `completion_time - request_time`

**示例**：
```
任务 2（长文总结）：
- 第 1 次：18 秒
- 第 2 次：22 秒
- 第 3 次：19 秒
- 平均：19.7 秒
```

**评分标准**（根据任务类型不同）：
- 短问答：< 10 秒
- 中等任务：< 30 秒
- 长文任务：< 120 秒

**指标 4：输出质量和格式遵守情况**

**评分方法**：

使用 3 级评分：
- ✅ 优秀：完全符合预期
- ⚠️ 一般：内容正确但格式不符
- ❌ 差：内容错误或不相关

**示例**：
```
任务 3（JSON 格式）：
- 第 1 次：✅（JSON 格式正确，字段完整）
- 第 2 次：⚠️（内容正确但字段名不同）
- 第 3 次：✅（JSON 格式正确，字段完整）
- 质量评分：67% 优秀，33% 一般
```

**指标 5：每次成功任务的实际费用**

**计算方法**：
```
单次成本 = 输入 Token × 输入单价 + 输出 Token × 输出单价
```

**示例**：
```
任务 2（长文总结）：
- 输入：2000 tokens × ¥108/M = ¥0.216
- 输出：150 tokens × ¥540/M = ¥0.081
- 单次成本：¥0.297

3 次测试总成本：¥0.891
```

**成本对比**：
```
平台 A：¥0.297/次
平台 B：¥0.350/次（慢 18%）
平台 C：¥0.250/次（快 16%）
```

**综合评分表**：

| 平台 | 成功率 | 首字延迟 | 完整响应 | 输出质量 | 单次成本 | 综合评分 |
|------|-------|---------|---------|---------|---------|---------|
| A | 95% ✅ | 2.1s ✅ | 19.7s ✅ | 89% ✅ | ¥0.297 | ⭐⭐⭐⭐⭐ |
| B | 88% ⚠️ | 3.8s ✅ | 25.3s ✅ | 92% ✅ | ¥0.350 | ⭐⭐⭐ |
| C | 98% ✅ | 4.2s ✅ | 22.1s ✅ | 85% ✅ | ¥0.250 | ⭐⭐⭐⭐ |

### 第 5 步：控制测试成本和风险

**操作**：

**成本控制**：

1. **使用小额余额**：
   - 每个平台充值 ¥5-10
   - 足够完成测试，避免浪费

2. **使用专用测试密钥**：
   - 为测试创建独立密钥
   - 测试完成后撤销（可选）

3. **限制重复次数**：
   - 每个任务重复 3 次足够
   - 不需要 10 次或更多

**风险控制**：

1. **使用非敏感材料**：
   - 不要用真实客户数据测试
   - 不要用公司机密文档测试
   - 使用公开文章或自己编写的测试文本

2. **不要压力测试**：
   - 不要突然发起大量并发请求
   - 可能违反服务条款
   - 可能导致账户被封禁

3. **间隔发送请求**：
   - 每个请求间隔 5-10 秒
   - 模拟真实使用场景

**测试成本预估**：

```
单个平台：
- 任务 1（短问答）：9 次 × ¥0.05 = ¥0.45
- 任务 2（长文总结）：9 次 × ¥0.30 = ¥2.70
- 任务 3（JSON 提取）：9 次 × ¥0.10 = ¥0.90
- 任务 4（质数列表）：9 次 × ¥0.03 = ¥0.27
- 任务 5（真实任务）：9 次 × ¥0.20 = ¥1.80
- 总计：¥6.12

3 个平台：
- 总计：¥18.36
- 建议充值：¥10 × 3 = ¥30（含余量）
```

### 第 6 步：得出可执行结论

**操作**：

**步骤 1：淘汰不符合最低要求的平台**

根据第 1 步定义的最低要求，淘汰不合格的平台。

**示例**：
```
最低要求：
- 成功率 > 95%
- 首字延迟 < 2 秒
- 单次预算 < ¥0.5

测试结果：
- 平台 A：成功率 95% ✅，首字延迟 2.1 秒 ⚠️，成本 ¥0.297 ✅
- 平台 B：成功率 88% ❌，首字延迟 3.8 秒 ❌，成本 ¥0.350 ✅
- 平台 C：成功率 98% ✅，首字延迟 4.2 秒 ❌，成本 ¥0.250 ✅

淘汰：
- 平台 B：成功率不达标（88% < 95%）❌
```

**步骤 2：比较剩余平台的优劣**

对剩余平台进行综合对比。

**示例**：
```
剩余平台：A、C

【平台 A】
优势：
- 成功率达标（95%）
- 首字延迟接近要求（2.1 秒，略超 2 秒）
- 输出质量稳定（89%）

劣势：
- 成本略高（¥0.297）

【平台 C】
优势：
- 成功率优秀（98%）
- 成本最低（¥0.250）

劣势：
- 首字延迟较慢（4.2 秒）
- 输出质量略低（85%）

【最终选择】
如果优先考虑响应速度：选择平台 A
如果优先考虑成功率和成本：选择平台 C
```

## 常见错误

### 错误 1：只测试一次就下结论

**症状**：
- 只在一个时间点测试
- 每个任务只执行 1 次

**危害**：
- 偶然的快速响应误导判断
- 无法发现晚间高峰的性能下降

**解决方法**：
- 至少 3 个时段（白天/晚间/周末）
- 每个任务重复 3 次

### 错误 2：没有定义最低要求就开始测试

**症状**：
- 测试完后不知道如何判断好坏
- 被某个平台的单次漂亮回答影响判断

**危害**：
- 主观判断，无法对比
- 选择不适合自己需求的平台

**解决方法**：
- 测试前写下最低要求
- 严格按照要求淘汰不合格平台

### 错误 3：测试任务不固定

**症状**：
- 每个平台用不同的测试任务
- 或使用不同的提示词

**危害**：
- 无法公平对比
- 结果不可信

**解决方法**：
- 所有平台使用相同的测试集
- 相同的提示词、相同的模型

### 错误 4：只看价格不看质量

**症状**：
- 只对比单次成本
- 忽略成功率、响应时间

**危害**：
- 选择了便宜但不稳定的平台
- 失败重试导致实际成本更高

**解决方法**：
- 先淘汰质量不达标的
- 再在剩余平台中比价格

### 错误 5：用敏感数据测试

**症状**：
- 用真实客户数据测试
- 用公司机密文档测试

**危害**：
- 数据泄露风险
- 违反公司规定

**解决方法**：
- 使用非敏感的公开文本
- 或自己编写测试文本
